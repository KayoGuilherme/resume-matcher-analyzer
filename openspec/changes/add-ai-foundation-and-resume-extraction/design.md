# Design

## Context

See proposal.md for motivation and the specs for behavior. Observed current state:

- `src/app/ai/` only has `parsing/`. `core/` has `config` (frozen `Settings`, only `database_url` is required), `db` (lazy, `lru_cache`d engine and sessionmaker, `get_session` dependency), `errors` (`DomainError` mapped in one place), `logging` (JSON logs; `QUIET_LIBRARIES` are capped at WARNING because pdfminer logs document tokens), `storage`.
- `resumes/` follows router -> service -> repository. `ResumeService` is built per request in `get_resume_service`. The repository commits inside its methods and maps rows to Pydantic models (`ResumeSummary`, `ResumeDetail`). The `resume` table has a unique `sha256`.
- Migrations `0001` (pgvector extension), `0002`, `0003` exist; `alembic/env.py` imports each model module; CI runs `alembic upgrade head`, `alembic check` and `pytest -m integration` against `pgvector/pgvector:pg16`. Unit tests run without a database and without environment variables (`tests/conftest.py` builds `Settings(...)` explicitly), so nothing may read settings at import time. `httpx` is already a dev dependency.
- The image is built with `uv sync --frozen --no-dev`; `uv.lock` is committed and CI uses `uv sync --locked`. Compose has `api` and `db` only.
- `.claude/CLAUDE.md` lists `ai/llm.py` and `ai/embeddings.py` as single files; the user asked to replace them with packages.

## Goals / Non-Goals

**Goals:**
- One provider-agnostic surface for LLM and embeddings; provider quirks (structured output support, temperature, flaky output) handled once, in shared code.
- Extraction output is trustworthy: validated by Pydantic, verbatim-checked against the resume text, experience duration computed by code.
- Everything testable with fakes or a mocked HTTP layer; no network in unit tests.
- Resume content never reaches logs, including third-party SDK debug logs.

**Non-Goals:**
- Jobs, matching, scoring, rewrite suggestions, evals, OCR.
- A job queue or worker process (FastAPI `BackgroundTasks` as requested).
- Streaming, tool-calling loops, multi-turn conversations, token budgeting, prompt caching.
- A re-embedding command (the procedure is documented; see Open Questions).
- Supporting Anthropic for embeddings (Anthropic has no embeddings model).

## Decisions

**1. Adapters are thin transports; one shared wrapper owns behavior.**
`ai/llm/base.py` defines the public `LLMClient` protocol (`async generate_structured[T: BaseModel](prompt: str, schema: type[T], *, system: str | None = None) -> T`; the optional `system` keeps the untrusted resume text out of the instruction channel), the error hierarchy (`LLMError` base; `LLMTransientError`, `LLMInvalidOutputError`, `LLMAuthError`, `LLMTimeoutError`; any other provider rejection is wrapped in the base `LLMError`, never a raw SDK exception) and the small internal `Transport` protocol that adapters implement: `complete(request) -> RawCompletion` where the request carries prompt, system, a JSON schema, `mode` (`native` or `prompt_json`) and an optional temperature, and the completion carries text/parsed JSON plus token usage. Adapters only translate to and from the SDK and map SDK exceptions to typed errors. `ai/llm/structured.py` holds `StructuredLLM(transport, settings)`, the only implementation of `LLMClient` used in production, and contains: backoff, mode fallback, temperature handling, JSON extraction, Pydantic validation, the repair attempt and logging. The adapter-level split is what satisfies "validation and retry logic live in the shared layer": a new adapter cannot forget them. `FakeLLMClient` implements `LLMClient` directly (scripted instances, raw texts that are validated like real answers, or errors; records calls) so unit tests of services never touch the wrapper, and wrapper tests use a fake `Transport`.
Alternative considered: each adapter implements `generate_structured` fully (what the brief literally lists). Rejected: validation/repair/fallback would be duplicated three times and tested three times.

**2. The structured-output flow.**
```
attempt(mode, temperature):
  native  -> transport.complete(mode=native)       # tool use / json_schema
  fallback-> transport.complete(mode=prompt_json)  # schema text appended to the prompt
call:
  1. mode = native unless this client already learned "unsupported"
  2. if the transport raises StructuredOutputUnsupported -> remember it, redo in prompt_json mode
  3. if it raises UnsupportedParameter("temperature") -> remember it, redo without temperature
  4. parse JSON (strip code fences / leading text) and validate with the schema
  5. invalid -> ONE repair call: original prompt + previous answer + the validation problems
     (field paths and messages), same mode; still invalid -> LLMInvalidOutputError
  6. LLMTransientError at any call -> backoff retry (decision 3); auth/timeout propagate
```
"Learned" flags (`native_supported`, `temperature_supported`) are plain attributes of the long-lived client; the factory returns one cached client per settings value (a lazy `lru_cache`, the same pattern as `db.get_engine`), so a fallback happens once per process, not once per request. Racing requests may both hit the fallback once; this is benign. Adapters decide "unsupported" from the provider's error shape: OpenAI-style `400` with `param`/`code` pointing at `response_format`/`tools`/`temperature`, Anthropic `400` whose message names `temperature`; these classifiers are unit-tested with recorded error bodies. Servers that accept `response_format` but ignore it simply return free text, which step 4-5 handle. Temperature is sent only if `LLM_TEMPERATURE` is not empty and not yet rejected; the default is 0 (some current models reject it, which is exactly the path in step 3).
The repair prompt is sent to the provider like any prompt and may contain resume content; it is never logged.

**3. Retry and errors: `core/retry.py` plus typed errors per layer.**
`retry_async(fn, *, is_retryable, attempts=3, base_delay=1.0, factor=2.0, max_delay=20.0)` with full jitter and an injectable `sleep` (tests pass a recorder; no real waiting). Used by both layers. Only transient errors are retryable. `Retry-After` is honored when the SDK exposes it (capped by `max_delay`). Timeouts are not retried: a slow local model will just time out again and the user-set timeout already bounds the wait. SDKs are created with `max_retries=0` so there is a single retry policy, and with `timeout=LLM_TIMEOUT_SECONDS`.
Embeddings define their own errors in `ai/embeddings/base.py` (`EmbeddingError`, `...TransientError`, `...AuthError`, `...TimeoutError`, `EmbeddingDimensionError`). Mapping an `LLMError`/`EmbeddingError` to a resume error code happens in one function in the resumes service (spec `resume-processing`), never in the AI layer.

**4. Adapters.**
- `anthropic_client.py`: `AsyncAnthropic(api_key, base_url?, timeout, max_retries=0, http_client?)`. Native mode: `messages.create` with one tool whose `input_schema` is the Pydantic JSON schema and `tool_choice` forcing it; the tool input is the structured answer. `prompt_json` mode: plain text answer. `max_tokens` is mandatory for Anthropic; a module constant (8192) is used, which fits a long resume. A `stop_reason` of `max_tokens` is reported as invalid output (truncated JSON), which the repair attempt cannot fix; it ends as `llm_invalid_output`.
- `openai_client.py`: `AsyncOpenAI(api_key or "not-needed", base_url?, ...)` using the Chat Completions API, because it is the one API every compatible server (Ollama, LM Studio, vLLM) implements; the newer Responses API is not universal. Native mode: `response_format={"type":"json_schema", ...}`. The schema is made strict-compatible (all properties required, `additionalProperties: false`) with the SDK's own helper, which means extraction schemas must avoid features strict mode rejects (no defaults relied on, optional values written as `X | None`); a test builds the strict schema for every schema class used in production. `provider=openai_compatible` and `provider=openai` share this class; they differ only in settings validation (base URL required vs optional, key required vs optional).
- Both accept an optional injected `httpx.AsyncClient`; adapter tests pass one with `httpx.MockTransport`, which is the "mocked HTTP layer" of the acceptance criteria and also exercises the real SDK parsing of responses and errors.
- Usage: `prompt_tokens`/`completion_tokens` (OpenAI) and `input_tokens`/`output_tokens` (Anthropic) normalized to `TokenUsage | None` (compatible servers sometimes omit it).

**5. Configuration and factory.**
`Settings` gains the `LLM_*` and `EMBEDDING_*` fields (see `app-configuration`). Provider fields are `Literal` types, so a bad value fails with the field name. API keys are `SecretStr`. `LLM_TEMPERATURE` uses a `field_validator(mode="before")` that turns an empty string into `None` (pydantic-settings would otherwise reject it for a float). Cross-field rules (key/base URL/model required per provider) are deliberately not validated in `Settings`: that would make `/health` and uploads fail for someone who has not configured an LLM. They are checked by the factories, which raise `AINotConfiguredError` (a `DomainError`, 503 `ai_not_configured`, defined in `ai/errors.py` and used by both factories), naming the setting and never a value. `get_llm_client(settings)` and `get_embedding_client(settings)` are FastAPI dependencies (`Depends`) and lazily cached per settings value (`lru_cache`, as `get_engine`); tests override them with the fakes through `dependency_overrides`. Because the settings object is frozen and hashable only if all fields are, `SecretStr` and `Path` are fine; the cache key is the settings instance itself.

**6. Embeddings layer.**
`ai/embeddings/base.py`: `EmbeddingClient` protocol (`async embed(texts: Sequence[str]) -> list[list[float]]`, plus `model_name` and `dimension` properties), errors. A shared `BatchingEmbeddingClient` wrapper (same idea as decision 1) splits inputs into batches of 64, retries transient errors, checks every vector has `EMBEDDING_DIMENSION` numbers (`EmbeddingDimensionError` naming both sizes) and logs. Adapters: `openai_client.py` (`embeddings.create`; serves `openai` and `openai_compatible`; sends `dimensions` only for provider `openai` with a `text-embedding-3*` model, so 1536/3072-native models can be cut to 1024), `local.py` (sentence-transformers; the model is loaded lazily on first use through an injectable loader, `encode` runs in `run_in_threadpool`, the import happens inside the loader so the module imports without the package; a missing package raises a clear error naming `uv sync --extra local-embeddings`) and `fake.py` (SHA-256 based deterministic unit-length vectors of the requested dimension).
Optional dependency: `[project.optional-dependencies] local-embeddings = ["sentence-transformers"]` (an extra, because it is a runtime feature, not a dev tool). Default `uv sync` and the default image do not install it. Dockerfile gets `ARG EXTRAS=""` and runs `uv sync --frozen --no-dev --no-editable $EXTRAS` (e.g. `--build-arg EXTRAS="--extra local-embeddings"`); compose does not enable it. mypy: `sentence_transformers` is imported inside a function and has `ignore_missing_imports` in a `[[tool.mypy.overrides]]` block, because CI does not install the extra; the adapter test injects a fake loader, so coverage does not need torch.
Torch note: on Linux `torch` resolves to a CUDA build by default (GBs). The README says to use the CPU index for the opt-in build; this is documentation, not configured by default.

**7. Embedding model default and the vector column.**
Default `bge-m3` via an OpenAI-compatible server (Ollama's `/v1/embeddings`), 1024 dimensions (comparison and reasons in proposal.md). `bge-m3` needs no `query:`/`passage:` prefixes (unlike E5 models, which would need prefix handling in the adapter), which keeps the adapter provider-agnostic. 2000 is pgvector's limit for HNSW on `vector`, hence the settings bound and the choice of 1024 over native 3072-dimension hosted models. The column is `vector(N)` where N is read from `EMBEDDING_DIMENSION` when migration `0004` runs; the SQLAlchemy model declares `Vector()` without a size, because the size cannot be read at import time (unit tests have no environment) and the real size lives in the database. `alembic check` must stay clean with this (verified in the integration job; see tasks and Risks).
Startup check: `check_embedding_dimension` runs in the lifespan. It reads `format_type(atttypid, atttypmod)` of `resume_chunk.embedding` from the catalog (`vector(1024)` -> 1024) and raises a `RuntimeError`-based `EmbeddingDimensionMismatchError` with the two sizes and the README section name. A missing table (migrations not applied) or an unreachable database (short connect timeout) logs a warning and continues, because `docker compose up` starts the API before `alembic upgrade head` has ever run.
Re-embedding procedure (documented in README, no code): vectors of different models are not comparable even at equal dimension. `SELECT embedding_model, count(*) FROM resume_chunk GROUP BY 1` shows stale chunks. Same dimension: change `.env`, restart, `POST /resumes/{id}/process` for each resume (this also re-runs extraction; the extra LLM cost is accepted for now). Different dimension: write a new migration (never edit `0004`) that drops the HNSW index, deletes the chunk rows (derived data), alters the column to `vector(N)`, recreates the index; run it with the new `EMBEDDING_DIMENSION`, restart, process again.

**8. Prompts: `ai/prompts/loader.py` and `.md` files.**
Each file starts with a front-matter block (`---`, `version: 1`, `---`). It is parsed by hand (a two-key header; no YAML dependency). `load_prompt(name) -> Prompt(name, version, text)` reads through `importlib.resources`, so it works from the non-editable wheel in the image (hatch includes non-Python files of `src/app`; a test builds the wheel path check and the docker-build job proves it). `Prompt.render(**values)` replaces `{{name}}` placeholders in one pass with a regex (values are inserted verbatim and never re-scanned, so resume text containing braces or `{{x}}` is safe) and raises on missing/unknown placeholders. `resume_extraction.md` has `{{resume_text}}` and `{{corrections}}` (empty on the first call). The resume goes between `<resume>` ... `</resume>` delimiters with the instruction that its content is data; this reduces, not eliminates, prompt injection, and the damage is bounded because output is schema-validated and verbatim-checked. The system/user split puts the instructions in `system` and the delimited resume in the user prompt.

**9. Extraction (`ai/extraction/`).**
Files: `models.py`, `verify.py`, `experience.py`, `resume.py`.
- Two model families. `ExtractedResume` is what the LLM is asked for: no ids, no totals, no contact fields (the schema simply has no field for them, and the prompt says to ignore them). `Resume` is the result: the same content plus code-assigned `id` (UUID) on each experience and project. The model never invents identifiers or totals, and an answer carrying extra fields (for example `total_years`) is ignored because the schema forbids/ignores unknown fields.
- `YearMonth` is a validated `YYYY-MM` string type (months 01-12). `Experience.is_current` is a boolean the model sets from words like "present"/"atual".
- `verify.py`: `is_verbatim(item, resume_text)` normalizes both sides with `unicodedata.normalize("NFKC")`, removes a leading bullet glyph from the item, and removes all whitespace, then tests substring containment. Removing all whitespace (not collapsing it) is deliberate: PDF line wraps and hyphenation (`micro- services`) otherwise cause false rejections; the cost is that `a b` equals `ab`, which does not matter for provenance. Case, accents and wording stay exact, so translations and paraphrases fail. `find_unverified(extracted, resume_text)` returns paths of failing bullets/skills lines; `drop_unverified(...)` removes them and returns the count.
- `resume.py::extract_resume(llm, prompts, resume_text, now) -> ExtractionResult`: render prompt (empty corrections) -> `llm.generate_structured` -> `find_unverified` -> if any, render again with a `corrections` block listing the offending items and asking for the exact text from the resume, call once more -> drop whatever is still unverified (count into `warnings`) -> assign ids -> compute totals -> return. Exactly one correction round (so at most two extraction calls, each possibly with its own transport-level repair). Invalid output after the repair attempt propagates as `LLMInvalidOutputError`; nothing partial is returned.
- `experience.py::total_experience_months(experiences, today)`: each valid experience becomes a `[start, end]` interval of month numbers (`year*12 + month`), inclusive; current ends at `today`; intervals are sorted and merged when they overlap or touch; the sum of merged lengths is the total. Invalid ones (no start, no end and not current, end < start) are skipped and counted into `warnings`. `years = round(months / 12, 1)`. `today` is a parameter, so tests need no clock patching.
- `ExtractionResult`: `resume`, `total_experience_months`, `total_experience_years`, `warnings` (stable codes with counts, e.g. `dropped_unverified_items: 2`, `experiences_without_valid_dates: 1`), `prompt_name`, `prompt_version`, `llm_provider`, `llm_model`, `extracted_at`. Provider/model names come from the client's settings (`LLMClient` exposes `provider` and `model` read-only attributes for this).

**10. Chunking (`ai/extraction/chunking.py`).**
Pure function `build_chunks(resume) -> list[ChunkDraft]` (`section`, `experience_id`, `position`, `text`). Order: skills lines, experience bullets (in resume order), project bullets; `position` is the running index. Summary, education, languages and certifications are not chunked (spec: bullets and skills lines only). Project bullets have no `experience_id` (projects have their own id in the extraction, but the chunk column is named for experiences as requested; see Open Questions).

**11. Pipeline (`ai/pipeline.py`).**
`process_resume_text(text, llm, embedder, prompts, now) -> ProcessedResume` = extract -> chunk -> `embedder.embed([c.text ...])` -> attach vectors and `embedder.model_name`. No database, no HTTP: a pure orchestration of small steps over Pydantic models, testable with both fakes.

**12. Persistence and migration `0004`.**
- `resume` gets `status` (text, not null, default `uploaded`, CHECK in the four values), `error_code` and `error_message` (text, nullable), `extraction` (JSONB, nullable). Existing rows become `uploaded`.
- `resume_chunk`: `id` UUID pk, `resume_id` UUID not null FK -> `resume.id` ON DELETE CASCADE (indexed), `section` text (CHECK), `experience_id` UUID null, `position` int, `text` text, `embedding` `vector(N)` not null, `embedding_model` text not null, `created_at` timestamptz. HNSW index `USING hnsw (embedding vector_cosine_ops)` with pgvector defaults (m=16, ef_construction=64). Chunks are a table, not JSON inside `resume`, because the vector index and later search need rows.
- The migration reads `EMBEDDING_DIMENSION` from `get_settings()` (alembic's `env.py` already uses settings for the URL), creates the column with raw SQL `vector(N)`, and imports are added to `env.py` for the new model. Downgrade drops the table and the columns.
- `pgvector` Python package provides the `Vector` SQLAlchemy type. With asyncpg, vectors may need a registered codec; if the plain bind processing does not work, an `event.listens_for(engine.sync_engine, "connect")` hook in `core/db.get_engine` registers it. This is the first thing the integration test for the repository settles (see tasks 6.x).

**13. Processing lifecycle (`resumes/service.py`, router).**
- `POST /resumes/{id}/process`: dependencies build the LLM and embedding clients first (so `ai_not_configured` fires before anything changes). The service runs one atomic statement `UPDATE resume SET status='processing', error_code=NULL, error_message=NULL WHERE id=:id AND status<>'processing' RETURNING ...`; no row -> either 404 or 409 (a follow-up read distinguishes them). This also makes concurrent requests safe without a lock. The router adds `background.add_task(service.run_processing, resume_id, llm, embedder)` and returns 202 with the resume.
- `run_processing` opens its own session from `get_sessionmaker(settings)` (the request session is closed when the response is sent), loads the text, calls `process_resume_text`, then `repository.save_processed(...)`: in one transaction delete old chunks, insert new ones, set `extraction`, `status='ready'`, clear the error. On any exception: map to an error code (one function: `LLMAuthError -> llm_auth_failed`, `LLMTimeoutError -> llm_timeout`, `LLMTransientError -> llm_unavailable`, `LLMInvalidOutputError -> llm_invalid_output`, `EmbeddingError` family `-> embedding_failed`, anything else `-> processing_failed` logged by type only) and `set_failed(...)` with a fixed per-code message (messages are constants, never built from exceptions). Old chunks and the old extraction are untouched because they are only replaced inside the success transaction.
- Startup (`lifespan`): `UPDATE resume SET status='failed', error_code='processing_interrupted', ... WHERE status='processing'`, next to the dimension check, both skipped with a warning if the database is unreachable or not migrated. This assumes one API process (documented; true for the current compose setup). With several workers this would fail rows that another worker is processing; a real job queue would be the fix and is a non-goal.
- `main.py` stays wiring only: the lifespan calls one function from `resumes` that does both startup tasks.

**14. API schemas.**
`ResumeSummary` gains `status` and `error: ResumeError | None` (`code`, `message`). `ResumeDetail` gains `extraction: ExtractionResult | None`. Both are additive. Vectors are never returned.

**15. Logging.**
`StructuredLLM` and the embedding wrapper log through `logging` with `extra`: provider, model, token counts, duration, outcome, attempt count; no content. `configure_logging` adds `openai`, `anthropic`, `httpx`, `httpcore` and `sentence_transformers` to `QUIET_LIBRARIES` (capped at WARNING): the OpenAI SDK logs request details at DEBUG and `httpx` logs URLs, so this is a privacy requirement, with a test that makes a mocked call at DEBUG and scans all captured logs for the prompt text. API keys are `SecretStr`, and adapter error messages are built from the status code and error type only (SDK exception strings can echo request fragments).

**16. Tests.**
- Unit (default run, no network): config validation; `core/retry`; `StructuredLLM` with a fake transport (valid, fenced JSON, fallback and remembering, repair success/failure counts, temperature rejection, retry/backoff with injected sleep, auth/timeout not retried); adapters over `httpx.MockTransport` (request shape: tool use vs `response_format`, headers, base URL, strict schema; response parsing; 400/401/429/5xx/timeout mapping; unsupported-feature classifiers; usage); embeddings wrapper (batching, order, dimension error, empty list), the OpenAI embeddings adapter over `MockTransport`, the local adapter with an injected loader; prompt loader; verbatim check (whitespace, bullets, ligatures via NFKC, accents, paraphrase, Portuguese); experience months (sequential, overlap, containment, adjacent, current, invalid, inclusive end); chunking; extraction with `FakeLLMClient`; pipeline with both fakes; service and router with fake repository/clients (202, 404, 409, 503, background success and each failure code); privacy log scans.
- Integration (`-m integration`, existing CI job): migration `0004` up/down, `alembic check`, `resume_chunk` insert/read through the repository (settles the asyncpg codec), cosine query uses the HNSW index (`EXPLAIN` with `enable_seqscan=off`), cascade delete, atomic replace and failure-keeps-old, dimension check match/mismatch/missing table, startup recovery of `processing`.
- `real_provider` marker, excluded by default (`addopts = ["-m", "not integration and not real_provider"]`) and by CI; a session fixture reads `get_settings()` and `pytest.skip`s with the missing setting's name. The LLM test sends a tiny schema; the embeddings test embeds two short PT/EN sentences and checks the dimension. Run with `uv run --env-file .env pytest -m real_provider`.

**17. Docker and docs.**
`docker-compose.yml` adds `extra_hosts: ["host.docker.internal:host-gateway"]` to `api` (Docker Desktop defines the name already; Linux does not). README: the Ollama steps (`ollama pull bge-m3`, `ollama pull <llm>`), and the point that Ollama listens on `127.0.0.1` by default, which a container cannot reach through the bridge gateway, so it must be started with `OLLAMA_HOST=0.0.0.0` (or bound to the docker bridge address), with the firewall caveat; LM Studio and vLLM equivalents; the `EXTRAS` build argument; the re-embedding procedure; what `ai_not_configured` means. `.env.example` gets all variables plus three commented blocks (Anthropic, OpenAI, Ollama). `.claude/CLAUDE.md` is updated: `ai/llm/` and `ai/embeddings/` packages (with their files), `ai/extraction/`, the rule "Only `ai/llm/` and `ai/embeddings/` call providers; business code depends only on the `LLMClient`/`EmbeddingClient` protocols", and the "Never call the LLM or embeddings provider outside ..." line reworded to the packages.

## Risks / Trade-offs

- [Verbatim check rejects legitimate bullets because PDF extraction garbles text (odd glyphs, broken ligatures)] -> NFKC and whitespace-insensitive comparison; a correction round; dropped counts surface as warnings so the problem is visible; tune later with evals.
- [Small local models fail often (invalid JSON, paraphrase, truncation)] -> shared repair and correction rounds, dropped items instead of bad data, a typed failure at the end; the provider is swappable by configuration. Context overflow shows up as a provider rejection (`llm_*` failure or `processing_failed`); input length limits are not enforced here.
- [Detecting "unsupported parameter" from provider error bodies is heuristic] -> classifiers are tested with recorded error shapes; anything unrecognized stays a plain failure instead of a silent fallback; servers that ignore the parameter are covered by validation + repair.
- [`alembic check` may report drift for `Vector()` without a size or the HNSW index options] -> verified in the first integration task; if it does, declare the index in the model with `postgresql_using="hnsw"` and `postgresql_ops` and, only if still needed, an `include_object` filter in `env.py`, documented there.
- [asyncpg and pgvector codec] -> settled by an early integration test; hook in `get_engine` if required.
- [Dimension is baked into the database at migration time from the environment] -> documented; the startup check makes a mismatch loud; the migration reads the setting at apply time, so the first `alembic upgrade head` needs the intended `EMBEDDING_DIMENSION`.
- [`BackgroundTasks` work dies with the process] -> startup marks stuck rows `failed`/`processing_interrupted`; single-process assumption documented.
- [Cached client instances hold learned flags] -> per-settings cache; flags only ever relax toward a working configuration; changing config means restarting the application anyway.
- [Prompt injection from resume text] -> delimiters plus a data-only instruction, schema validation, verbatim check; no tool access exists, so the blast radius is the extraction content itself.
- [Local embeddings pull torch (GBs, CUDA wheels)] -> optional extra, not in the default image, CPU-index note in the README.
- [Hosted providers receive resume text] -> the README states it plainly next to the provider examples; the default embeddings provider is local.
- [Re-processing re-runs the LLM to change embeddings only] -> accepted cost for a single-user tool; a dedicated re-embed command is an easy later change since extraction is stored.

## Migration Plan

1. Deploy the code, set `EMBEDDING_*` (and `LLM_*` to use extraction), then run `alembic upgrade head` (applies `0004`; existing resumes become `uploaded`; `resume_chunk` is created with the configured dimension).
2. Restart the API; the startup check confirms the dimension.
3. `POST /resumes/{id}/process` for the resumes to process.
Rollback: `alembic downgrade 0003` drops `resume_chunk` and the new `resume` columns (extraction data is derived and can be regenerated); the application of this change must be rolled back with it, since the code expects the columns.

## Open Questions

- Should project bullets carry the project's id in a general `entry_id` column instead of leaving `experience_id` null? Chosen for now to follow the brief (`experience id`); a later matching change can rename it without touching behavior of this one.
- Should education, certifications and the summary also become chunks? Not required by the brief; matching can add them later because the extraction is stored.
- A dedicated "re-embed from stored extraction" command is deferred; the documented procedure re-runs extraction.
- Retry constants (3 attempts, 1 s base, 20 s cap), embedding batch size (64) and the 8192 `max_tokens` for Anthropic are fixed constants, not settings; they can become settings if real use shows the need.
