# Design

## Context

See proposal.md for motivation and the specs for behavior. Observed current state (after `add-ai-foundation-and-resume-extraction` and `add-job-positions`, both still to be merged):

- `resumes/` and `jobs/` share one pattern: router -> service -> repository, an atomic start of processing, a `BackgroundTasks` job that opens its own session through a `get_*_background_service_factory` dependency, AI clients as `Depends` (so a missing configuration answers 503 before anything changes), `mark_interrupted` at startup (`run_startup`, `run_jobs_startup` in the lifespan), and `PROCESSING_MESSAGES` / `processing_error_code` / `AlreadyProcessingError` shared through `core/processing.py` and `ai/error_codes.py`.
- Resume data: `resume.text` (the parsed text), `resume.extraction` (`ExtractionResult`: `Resume` with experiences with `start`/`end`/`is_current`, bullets, skills lines, education, languages with their level as written, certifications, projects; plus `total_experience_months`), and `resume_chunk` rows (skills lines, experience bullets, project bullets; `vector(N)` + `embedding_model`). Summary, education, languages and certifications are **not** chunked.
- Job data: `job.extraction` (`JobExtractionResult` with `Job`: language, seniority, `ats_keywords` normalized, requirements with `category`, `priority`, `priority_unclear`, `min_years`, normalized keywords with synonyms, `source_text`) and `job_requirements` rows with the vector and `embedding_model`.
- Profile: `ProfileOut` (stacks with normalized `name`, `years`, `level`; languages with normalized `name` and CEFR `level`; `total_years_coding`; `notable_facts`).
- `ai/extraction/verify.py` has `normalize` and `is_verbatim` (NFKC, all whitespace removed, leading bullet ignored; words, accents and case exact). `ai/extraction/experience.py` has `total_experience_months` (merged inclusive months). `core/normalization.py` has `normalize_stack_name`, `normalize_language_name`, `fold_text` and the alias tables (alias -> canonical only).
- `LLMClient.generate_structured(prompt, schema, system=...)` returns a validated model; the sampling (temperature 0 by default) is the client's configuration; `StructuredLLM` already repairs and retries internally.
- No `ai/matching/` and no `analyses/` exist. The brief asks for both; `.claude/CLAUDE.md` already names `analyses` as a feature folder, and `ai/matching/` is the one new folder (added to the folder structure in the docs task).

## Goals / Non-Goals

**Goals:**
- Every positive verdict is provable: a resume quote that really is in the resume, or a profile fact. The proof is enforced in one place, after all steps, not trusted to the model.
- Spend tokens only where cheap steps cannot decide: deterministic proof and "nothing similar" are settled in code.
- Each step is a small pure function over Pydantic models, testable with exact expectations and fakes; the DB and the LLM appear only at the edges (repository, `LLMClient` protocol).
- Reuse the shared AI layer, the processing lifecycle and the verbatim check; no new dependency.

**Non-Goals:**
- Scoring, a final decision, rewrite suggestions (later changes), listing/deleting analyses, partial re-runs, streaming progress, concurrent LLM calls, a re-embedding command.

## Decisions

**1. Package layout.**
`ai/matching/` (pure, no DB, no HTTP): `models.py`, `errors.py`, `text.py` (literal matching), `levels.py` (language levels), `deterministic.py`, `retrieval.py`, `judge.py`, `profile_check.py`, `ats.py`, `cache.py` (cache key), `engine.py` (`analyze(...)`), plus `ai/prompts/gap_judge.md`. `analyses/` (feature): `router.py`, `schemas.py`, `models.py`, `repository.py`, `service.py`, `startup.py`. `ai/matching/` does not import any feature package: the service maps database rows to the small input models of `ai/matching/models.py` (`ResumeInput`, `ChunkInput`, `JobInput`, `RequirementInput`, `ProfileFacts`). This keeps `ai/` free of feature coupling (`tests/ai/test_architecture.py` keeps passing) and makes the engine usable from `evals/` later.

**2. Inputs, and who reads what.**
`AnalysisService` is built from `AnalysisRepository`, `ResumeRepository`, `JobRepository` and `ProfileRepository` (repositories of other features, never their services). Two read methods are added, DB access only: `ResumeRepository.get_chunks(resume_id)` (a `StoredChunks`: the chunks as `ChunkInput` with their vectors, in resume order, and the set of embedding models) and `JobRepository.get_requirement_vectors(job_id)` (a `StoredVectors`: requirement id -> vector, and the set of embedding models). The resume text and extraction come from `ResumeDetail`, the job from `JobDetail`. The engine receives a snapshot loaded once at the start, so a resume or job processed again while an analysis runs cannot mix two versions.

**3. The pipeline per requirement (`engine.analyze`).**
`analyze(inputs, llm, settings_snapshot, now) -> AnalysisResult`:
1. For each requirement, `deterministic.check` -> a `Settled(verdict, evidence, explanation_code)` or a `Hints` object (computed years, matched keyword chunks, language levels) -- never a negative except "education section absent".
2. Not settled: `retrieval.candidates` -> candidates, or `Settled(missing, "no_similar_content")`.
3. Not settled: the requirement joins the judge queue with its candidates and hints.
4. `judge.run` over the queue in batches; each answer goes through `verify_answer` (the evidence rule).
5. `profile_check` over every finding that is `missing` or `partial`.
6. `finalize` validates the invariants of the evidence rule for **every** finding with a defensive pass that raises `AnalysisInvariantError` (an invariant break is a bug in a step: the analysis fails as `processing_failed` and only the exception type is logged, so an unproven `met` can never be stored), then assembles the `AnalysisResult` with the ATS coverage, warnings and provenance.
The steps are plain functions; only `judge.run` is async (it awaits the LLM). Requirements are processed in job order; the result list keeps that order whatever step settled each.

**4. Literal matching (`ai/matching/text.py`).**
One function builds the "forms" of a keyword: its normalized name, its synonyms and the inverse aliases (`core/normalization.py` gets `aliases_of(canonical)` over `STACK_ALIASES` and `LANGUAGE_ALIASES`; a requirement of category `language` uses the language aliases). The text is searched with `fold_text` applied to both sides (accent-free, lowercase, single spaces) and a regular expression with look-around: `(?<![\w+#])FORM(?![\w+#])`, `FORM` escaped. A trailing `.` after the form is allowed (end of a sentence), `.net` and `node.js` contain their dots. Single-character look-arounds are enough for the cases of the specs (`java`/`javascript`, `c`/`c++`/`c#`, `go-to-market` still matches `go`, which is why forms of one or two characters never settle a requirement alone: `AMBIGUOUS_MAX_LENGTH = 2`). The result of a search is the list of match spans mapped back to the original text, so the matched text "as written" and the containing bullet or line can be returned. The ATS coverage uses the same search without the ambiguity rule, because an ATS matches the literal word.
Folding changes lengths only for accent removal and whitespace collapsing; the search runs on the folded text and each hit is mapped back to the original with an index map (the same technique `priority.py` uses to locate `source_text`), because the evidence quote must be the original wording.

**5. What a quote is, and how a deterministic match produces one.**
Evidence from a deterministic match is the text of a chunk (a bullet or skills line, already verified verbatim at extraction) that contains the match; when the match is outside the chunks (education, languages, summary), it is the resume's own line (the text between line breaks of `resume.text`) containing it, cut to a stretch of at most 400 characters that holds the match (any stretch of the text is still verbatim). At most 3, in resume order. Quotes are re-checked with `verify.is_verbatim` against the resume text by the final pass anyway, so a bug here fails loudly instead of leaking an invented quote.

**6. Years (`deterministic.years`).**
Reuses `total_experience_months` on the experiences selected for the requirement: all of them when the requirement has no keywords, otherwise those whose title or any bullet contains a keyword form (same search, ambiguity rule applied: one- and two-character names select nothing). `ExperienceTotal.years` (rounded to one decimal) is compared with `min_years` using the unrounded months (`months / 12 >= min_years`). The experiences come from `resume.extraction`, so the dates are the extraction's `YYYY-MM` values; skipped experiences are reported in the hint (for the judge) but never count. Only "reaches the minimum" settles. The hint (`resume_years`, `profile_years`) is shown to the judge so that "3 of 5 years" can become `partial` with a quote.

**7. Language level (`levels.py`).**
A table of folded words and codes (English and Portuguese) to a rank on `A1 < A2 < B1 < B2 < C1 < C2 < native`: `beginner/iniciante` A1; `basic/elementary/basico/elementar` A2; `intermediate/intermediario` B1; `upper-intermediate/intermediario avancado` B2; `advanced/avancado/fluent/fluente/proficient/proficiente` C1; `bilingual/bilingue` C2; `native/nativo/nativa` native; the CEFR codes themselves. The longest phrase wins over its parts (`upper-intermediate` before `intermediate`), codes match as whole tokens. The asked level is read from the requirement's `text` only (its `source_text` can be a sentence shared with another requirement, for example "Fluent English and basic Spanish", so it could give one language the other's level) and takes the highest rank found (the conservative reading for a deterministic `met`); no level word means "any level". `resume_level(language)` reads the level string as the resume wrote it (`LanguageSkill.level`); unparseable is "unknown" and proves nothing when a level is asked. The language of a requirement is the normalized name of its first keyword (extraction already normalizes language keywords with `normalize_language_name`). The profile has exact CEFR levels, so `profile_check` compares ranks directly.
Alternative: ask the judge for levels. Rejected: it is cheap to do in code, exactly testable, and the profile cross-check needs the same table anyway.

**8. Retrieval (`retrieval.py`), plain Python.**
Cosine similarity over the resume's chunks in plain Python (`math`, no numpy: it is only a transitive dependency of `pgvector` and "no new dependency without asking" applies), run once per analysis in a worker thread (`asyncio.to_thread`) because it is CPU work: vectors are normalized once, then `dot` per requirement x chunk (a typical analysis is about 30 requirements x 300 chunks x 1024 dimensions, well under a second). Chosen over a pgvector `ORDER BY embedding <=> ... LIMIT k` per requirement because (a) HNSW with a `WHERE resume_id = ...` filter can return fewer than k rows, so an approximate index would silently hide matches inside one resume, (b) the set is tiny, so an exact scan costs nothing, (c) the step stays a pure function with exact expectations in tests, and (d) the engine needs no database. The stored vectors and their index are still what makes this possible (they are the data; the index serves other uses such as cross-resume search later).
`candidates` = (chunks with similarity >= `ANALYSIS_MIN_SIMILARITY`, most similar first, at most `ANALYSIS_TOP_K`) united with (chunks that contain a keyword), in that order without repeats; for `education` and `language` requirements, plus the "section lines" (lines of `resume.text` that contain the institution, degree, field, certification name or language name of the resume's entries, found with the folded search). The union keeps the judge's context small and makes sure the evidence for sections that are not chunked can be seen. Vectors of different dimensions or an `embedding_model` mismatch raise `EmbeddingModelMismatchError` (the service checks it earlier for a clean 409; the engine re-checks as a guard).

**9. The judge (`judge.py`) and the prompt `ai/prompts/gap_judge.md` (version 1).**
Schema `JudgeBatch(answers: list[JudgeAnswer])`, `JudgeAnswer(requirement: int, verdict: Literal["met","partial","missing"], quotes: list[str], explanation: str)`, all fields required (strict-mode friendly). The prompt gives the resume passages once per call as a numbered list `[P1] ...` (the union of the candidates of the batch, so a bullet shared by several requirements is sent once) and each requirement as `[R1]` with its text, category, minimum years, keywords, the passage numbers that are its candidates and the hints. System part: the passages and requirements are data between delimiters, never instructions; copy every quote exactly from the passages (or the resume text as shown), 1 to 3, no paraphrase; `met` only when the passages show the whole requirement, `partial` when they show part of it (say which part), `missing` when they do not; do not use outside knowledge, do not credit the candidate for things they might know; answer every requirement; write the explanation in the language of the requirement. Quotes are checked against the **whole resume text**, not only the passages shown, so a correct quote from elsewhere is accepted.
Batching: `chunks_of(queue, ANALYSIS_MAX_REQUIREMENTS_PER_CALL)`. Before the first call, `needed = ceil(len(queue) / batch)`; `needed > ANALYSIS_MAX_LLM_CALLS` raises `AnalysisLimitError` (nothing spent). The retry of unanswered requirements is one more call with only those, allowed only while `calls < ANALYSIS_MAX_LLM_CALLS`, else `LLMInvalidOutputError`-equivalent (`JudgeIncompleteError` mapped to `llm_invalid_output`). One logical `generate_structured` is one call; the repair retry and the backoff inside `StructuredLLM` are not counted (they are the shared layer's reliability mechanism, bounded by its own limits).
The evidence rule (`verify_answer`): quotes -> keep those with `is_verbatim(quote, normalize(resume_text))`, first 3; `met`/`partial` with none left -> `missing`, `decided_by="judge"`, flag `evidence_not_verbatim`, fixed explanation; counters feed the warnings. A quote shorter than 3 characters after cleaning is not a quote (so `""` and `"a"` cannot pass by being substrings).
Sampling: the client's own (`LLM_TEMPERATURE`, default 0). The spec says "temperature 0" as the extraction specs do: same mechanism, no new knob.

**10. Profile cross-check (`profile_check.py`).**
Pure function `check(requirement, finding, profile, hints) -> Finding`. Order: (1) stack match: any requirement keyword form equals a profile stack `name` (both normalized; synonyms and aliases included), level != `learning`, years >= `min_years` when stated; (2) no keywords and `min_years`: `total_years_coding >= min_years`; (3) `language`: profile language with the same normalized name and rank >= required rank; (4) no `min_years`: a notable fact containing a keyword form as a whole term (ambiguity rule applies: short forms do not match facts). Evidence is composed from profile values (`"python: 6 years, expert"`, `"english: C1"`, `"<n> years coding in total"`) or is the fact verbatim. It applies to `missing` and `partial`; a `partial` finding keeps its resume quotes first. This is a documented extension of the brief ("if the resume does not show it but the profile does"): a partial verdict means the resume does not show the whole requirement, and a candidate who has 6 years where the resume shows 3 should be told.
The profile check never calls the LLM and never *reads* the resume.

**11. ATS keyword coverage (`ats.py`).**
For each `ats_keywords` entry (already normalized by the job extraction): forms = the name plus `aliases_of(name)`; searched in the resume text; `found` carries the matched text as written; `missing` the rest. No percentage. No ambiguity rule (a literal ATS does not have one), no requirement synonyms (those belong to the requirement; coverage is about the posting's own keyword list).

**12. Result model and storage.**
`AnalysisResult` (in `ai/matching/models.py`): `findings: list[RequirementFinding]`, `ats_coverage: AtsCoverage(found: list[FoundKeyword], missing: list[str])`, `warnings: list[ExtractionWarning]` (reused model: stable code + count), `provenance` (`prompt_name`, `prompt_version`, `llm_provider`, `llm_model`, `embedding_model`, `llm_calls`, `top_k`, `min_similarity`, `max_requirements_per_call`, `max_llm_calls`, `analyzed_at`). Table `analysis`: `id` UUID pk, `resume_id` FK -> `resume.id` ON DELETE CASCADE, `job_id` FK -> `job.id` ON DELETE CASCADE (both indexed), `status` text with CHECK (`processing`, `ready`, `failed`), `error_code`, `error_message` null, `cache_key` text (64 hex), `result` JSONB null, `created_at`, `completed_at` null. A partial unique index `uq_analysis_cache_key_active` on `cache_key` WHERE `status IN ('processing','ready')` makes "one active analysis per inputs" a database rule (migration `0006`). No vector column, so no dimension check. The whole result is one JSON document: findings are always read together, nothing queries individual findings yet, and a later change (score) reads this document.

**13. Cache key (`cache.py`).**
`cache_key = sha256(canonical JSON of {resume_id, job_id, judge_prompt: "name:version", llm: "provider/model", settings: {top_k, min_similarity, max_requirements_per_call, max_llm_calls}, inputs: sha256 of canonical JSON of {resume.extraction, resume embedding_model, job.extraction, job embedding_model, profile}})`. The brief says "(resume_id, job_id, prompt versions)". Those three alone would return a stale result after the candidate edits the profile (the very action the main finding asks for), after reprocessing a resume or a job (new extraction, new chunk and requirement ids) or after changing a threshold, so the key also carries a fingerprint of the stored processing results, the profile, the LLM identity and the settings. `extraction` contains `extracted_at` and per-run ids, so a reprocessed resume or job always gets a new key even if its content came out the same (safe side). A tested pure function; the same inputs always give the same key.
`POST /analyses` flow in `AnalysisService.request`: (1) load resume, job (404s), (2) readiness checks in the order of the spec, (3) load profile, chunk/requirement embedding models and compare, (4) compute the key, (5) `repository.find_active(key)`: `ready` -> 200, `processing` -> 202, none -> `repository.create(...)` which inserts `processing` with `ON CONFLICT DO NOTHING` on the partial unique index and, when the insert lost the race, returns the winner's row (so two simultaneous requests share one run), (6) the router schedules the background run only when this request created the row. The service returns `(analysis, started: bool)`; the router maps `ready` -> 200, otherwise 202.

**14. Background run and failure handling.**
Like `JobService.run_processing`: `run(analysis_id, llm)` reloads the snapshot with its own session, calls `analyze` and `repository.save_result` (one UPDATE `status='ready'`, `result`, `completed_at`, `WHERE id = ... RETURNING`, False when the row is gone), never raises: any exception becomes `failed` with `processing_error_code(error)` and a fixed message from `PROCESSING_MESSAGES`. New errors in `ai/matching/errors.py`: `AnalysisLimitError` -> `analysis_limit_exceeded`, `EmbeddingModelMismatchError` -> `embedding_model_mismatch`, `JudgeIncompleteError` -> `llm_invalid_output`, `AnalysisInvariantError` -> `processing_failed`; `ai/error_codes.py` maps them (`ai/matching/` must not import `ai/error_codes.py`, so there is no cycle). `PROCESSING_MESSAGES` gets the two new codes. `analyses/startup.py` has `run_analyses_startup(settings)` like the jobs one (no dimension check) and the lifespan calls it.
The 409 `DomainError` subclasses live in `analyses/service.py` (`ResumeNotReadyError` `resume_not_ready`, `JobNotReadyError` `job_not_ready`, `ProfileRequiredError` `profile_required`, `EmbeddingModelsDifferError` `embedding_model_mismatch`); the engine's own `EmbeddingModelMismatchError` (same code) is the run-time guard and is not a `DomainError`, because by then there is no request to answer.

**15. Explanations written by the system.**
`ai/matching/messages.py`: fixed templates per code and language (`en`, `pt`; `other` -> `en`): `keyword_found`, `years_reached`, `language_level_reached`, `education_section_absent`, `no_similar_content`, `evidence_not_verbatim`, `in_profile_not_in_resume_skill|years|language|fact`. Templates take only the requirement `text`, counts and matched names (never other content) as parameters. Judge explanations are the model's, in the requirement's language, with the downgrade rule above.

**16. Logging.**
Counts only: `analysis started` (ids), `analysis finished` (ids, counts by verdict and by `decided_by`, `llm_calls`, warning codes, duration), `analysis failed` (ids, error code, exception type, duration). No text of resume, job, profile, requirements, quotes or explanations; a test captures all records at DEBUG and searches for known strings.

## Risks / Trade-offs

- **A deterministic `met` can overstate** ("Kubernetes" in a skills line proves the word, not production use). Accepted on purpose for a first ATS screening: a literal match is exactly what an ATS checks, the evidence is shown to the user, and requirements with years, language levels and education wording have their own stricter rules. The ambiguity rule keeps `go`, `c`, `r` out. A later change can add a "needs judge" flag for requirements whose text has qualifiers.
- **`missing` from retrieval can hide evidence outside chunks** (summary, certifications for non-education requirements). Mitigated: keyword chunks are always candidates, `education` / `language` get section lines, and the profile cross-check still runs. The summary is not searched; if that matters, `build_chunks` can include it later (re-embedding needed).
- **`ANALYSIS_MIN_SIMILARITY` depends on the embedding model.** 0.4 is a conservative starting point for `bge-m3`, documented in the README as something to tune with the evals; too high means many `missing` by retrieval, too low means more judge calls.
- **Cache key is wider than the brief** (fingerprint of the stored results, profile, LLM and settings). Costs a few extra analyses after edits; prevents stale answers. Flagged in the proposal.
- **Cap on calls is a hard failure**, not a partial result: a large posting needs the limits raised in config. Chosen over silently judging only the first N requirements, which would hide gaps.
- **Plain-Python cosine** is slower than SQL or numpy for big resumes; at the sizes of this product it is fast and the work is off the event loop. If resumes grow far beyond that, switching to a SQL query changes `retrieval.py` only.
- **Sequential judge calls**: simple and respects rate limits; an analysis of 30 requirements is about 4 calls.

## Open Questions

None blocking. Assumptions recorded above, to confirm in review: the wider cache key (decision 13), the profile cross-check also applying to `partial` (decision 10), `409 profile_required` for a missing profile, and `202`/`200` for new/cached analyses.
