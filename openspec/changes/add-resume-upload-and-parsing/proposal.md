# Proposal

## Why

An ATS first reads the text of the resume. If that text cannot be extracted cleanly (scanned pages, columns that interleave, tables, text hidden in headers), the candidate fails before any AI looks at the content. This change imports resumes and reports how readable they are, so later changes (LLM extraction, matching, analysis) can build on text that is known to be extractable.

## What Changes

- Add the `resumes` feature (`src/app/resumes/`: router, schemas, models, repository, service) with four endpoints: `POST /resumes` (multipart upload of a PDF or DOCX), `GET /resumes`, `GET /resumes/{id}` and `DELETE /resumes/{id}`.
- Add `src/app/ai/parsing/`: turns PDF (pdfplumber) and DOCX (python-docx) bytes into plain text plus facts about the document, and a parsing-quality check that returns a list of issues (code, severity, message). CPU-bound parsing runs in a threadpool.
- Quality issues detected: image-only/scanned PDF, multi-column layout, tables, content in header/footer, very low text-to-page ratio, icon/special glyphs used as bullets, missing standard sections (experience, education, skills; English and Portuguese headings), and more than 3 pages.
- Upload rules: the real file type is checked from the file content (magic bytes), not the extension; maximum size 5 MB (configurable); empty files and files with no extractable text are rejected with an error that explains the ATS problem. Uploading the same bytes again (same sha256) returns the existing resume instead of creating a duplicate.
- Store the original file behind a `FileStorage` interface with a local-disk implementation (directory from configuration). Store the extracted text, sha256, page count and parsing metadata/issues in a new `resumes` table (migration `0003`).
- New settings `RESUME_MAX_UPLOAD_BYTES` and `RESUME_STORAGE_DIR` (in `.env.example`); the Docker setup gets a persistent, writable volume for uploaded files.
- Privacy: resume text and file names are never logged; stored files are named by content hash, not by the uploaded name.
- Tests with generated fixtures: a clean one-column PDF, a two-column PDF, a DOCX, a scanned (image-only) PDF and a fake file with a `.pdf` extension; unit tests (parsing, service, repository, router, storage), and `integration` tests for the real database and disk.

### New dependencies (justification, per project rule)

| Package | Why it is needed | Notes |
|---|---|---|
| `pdfplumber` | Requested. Text, word positions, tables and images per page, which the layout checks (columns, header/footer, tables, scans) need; a plain text extractor would not give positions. | Pure Python wheel with `py.typed`. Pulls `pdfminer.six`, `Pillow`, `pypdfium2` (binary wheels, no system packages needed on `python:3.12-slim`). |
| `python-docx` | Requested. Reads DOCX paragraphs, tables, headers/footers and section column settings. | Pure Python wheel with `py.typed`, MIT. Pulls `lxml` (binary wheels). |
| `python-multipart` | Not requested, but required by FastAPI to receive `multipart/form-data` (`UploadFile`); without it the upload endpoint cannot be declared. | Tiny pure Python wheel, Apache-2.0, `py.typed`. |

No other runtime or dev dependency is added: file type detection uses the standard library (`zipfile` and magic bytes), hashing uses `hashlib`, and the test PDFs/DOCX are generated by a small test helper (DOCX with `python-docx`, PDFs with a minimal hand-written PDF writer) instead of adding a PDF-writing library.

## Capabilities

### New Capabilities
- `resume-management`: uploading, listing, reading and deleting resumes; upload validation and rejection errors; de-duplication by content hash; original file storage; privacy of resume content in logs.
- `resume-parsing`: extracting plain text and document facts from PDF and DOCX, and the parsing-quality report (issue codes, severities, messages) shown to the candidate.

### Modified Capabilities
- `app-configuration`: two new settings (maximum upload size, resume storage directory) with defaults, listed in `.env.example`.
- `container-runtime`: uploaded files live in a persistent volume that the non-root API user can write to.

## Impact

- New code: `src/app/resumes/{__init__,router,schemas,models,repository,service}.py`, `src/app/ai/__init__.py`, `src/app/ai/parsing/` (text extraction and quality checks), `src/app/core/storage.py` (the `FileStorage` interface and local-disk implementation), `alembic/versions/*-0003_*.py`, tests under `tests/resumes/`, `tests/ai/parsing/` and `tests/core/`, and a test fixture builder.
- Modified: `pyproject.toml` and `uv.lock` (three dependencies), `src/app/core/config.py` (two settings), `src/app/main.py` (router), `alembic/env.py` (import the model), `.env.example`, `docker-compose.yml`, `Dockerfile` (storage directory owned by the API user), `.gitignore`/`.dockerignore` (local `data/` directory), `README.md`.
- New public API: `POST /resumes`, `GET /resumes`, `GET /resumes/{id}`, `DELETE /resumes/{id}`. No existing endpoint changes.
- Resume text and files are personal data: never logged, never in error messages, stored only in the database and the storage directory.
- Single user, no authentication (as for the candidate profile).
- Out of scope: LLM extraction, embeddings, jobs, analysis, OCR of scanned files, pagination, editing or re-parsing a stored resume.
